Section 01

Cache

Store expensive responses and frequently accessed data in memory — so the next request is served in a fraction of the time.

Section one: cache.
Cache · Definition

What is a cache?

A cache is a temporary storage area that stores the result of expensive responses or frequently accessed data in memory, so that subsequent requests are served more quickly.

The problem

Every time a new web page loads, one or more database calls are executed to fetch data. Calling the database repeatedly greatly affects application performance.

The fix

Put a cache between the web servers and the database. Repeated reads are answered from memory, and the database only sees the requests the cache can't serve.

Key idea: the database is the expensive part. If a thousand users request the same profile, we shouldn't run the same query a thousand times. Memory is much faster than disk-backed databases, so we keep the hot results there.
Cache tier · Figure 1-7

A separate cache tier — read-through strategy

Better system performance Reduced database workload Scale the cache tier independently
Data exists in cache → the web server reads it from the cache and returns it. No database call.
Data not in cache → query the database, store the response in the cache, then return it to the client.
The cache tier is a temporary data store layer, much faster than the database. Walk through both cases with the toggle. This pattern — check cache first, on miss load from DB and populate cache — is called read-through. Other strategies exist depending on data type, size, and access patterns.
Cache · API

Talking to a cache is simple

Most cache servers expose APIs for common programming languages. Typical Memcached API:

memcached — from the book
SECONDS = 1
cache.set('myKey', 'hi there', 3600 * SECONDS)
cache.get('myKey')
set(key, value, ttl) — store a value that expires after 3600 s (1 hour).
get(key) — returns the value, or nothing if it's missing/expired.
read-through, in practice (illustration)
def get_user(user_id):
    key = f"user:{user_id}"
    user = cache.get(key)
    if user is None:        # cache miss
        user = db.query_user(user_id)
        cache.set(key, user, 3600)
    return user             # hit or filled
The left snippet is exactly the book's example. On the right is how read-through looks in application code — this is my illustration to connect it with the previous slide, not from the book.
Considerations for using cache · 1/3

When to cache, and for how long?

When to use

  • Data is read frequently but modified infrequently.
  • Cache lives in volatile memory — if the cache server restarts, all data is lost.
  • Important data must be saved in persistent data stores.

Expiration policy

Expired data is removed. Without a policy, data stays in memory forever. Drag the TTL:

short TTLlong TTL
Reloads from DB
Risk of stale data
Balanced ✓

Consistency

  • Keep the data store and cache in sync.
  • Inconsistency happens because data-modifying operations on the store and the cache are not in a single transaction.
  • Across multiple regions it's challenging — see “Scaling Memcache at Facebook”.
Three considerations. One: only cache read-heavy, rarely-changing data, and never treat the cache as the source of truth. Two: expiration — use the slider: too short means we keep reloading from the database; too long means users see stale data. Three: consistency — updating DB and cache isn't atomic, so they can drift, especially across regions.
Considerations for using cache · 2/3

Mitigating failures — avoid the SPOF

“A single point of failure (SPOF) is a part of a system that, if it fails, will stop the entire system from working.”

✕ One cache server

→
→

If it goes down, every request suddenly hits the database.

✓ Recommended

  • Multiple cache servers across different data centers.
  • Overprovision the required memory by a certain percentage — a buffer as memory usage grows.
A single cache server is a single point of failure — the book's example is a single router in front of an application server. The fix: several cache servers spread over data centers, and overprovision memory so growth doesn't push us into constant eviction.
Considerations for using cache · 3/3

Eviction policy — what leaves when the cache is full?

Once the cache is full, adding an item may remove an existing one. This is called cache eviction.

LRU live demo · capacity = 4

← most recently usedleast recently used →

LRU · Least Recently Used

Evict the item that hasn't been accessed for the longest time. The most popular policy.

LFU · Least Frequently Used

Evict the item with the fewest accesses.

FIFO · First In, First Out

Evict the oldest inserted item, regardless of usage.

The demo runs the access sequence through an LRU cache of size four. A hit moves the key to the front. A miss on a full cache kicks out the rightmost — least recently used — key. LFU and FIFO are alternatives for different use cases.

Section 02

Content Delivery Network

A network of geographically dispersed servers that deliver static content from the location closest to the user.

Section two: CDN.
CDN · How it works · Figure 1-9

Closer servers → faster pages

CDN servers cache static content: images, videos, CSS, JavaScript files, etc.

.png / .jpg.mp4.css.js

When a user visits a website, the CDN server closest to the user delivers the static content. The further the user is from CDN servers, the slower the site loads.

Dynamic content caching (HTML pages based on path, query strings, cookies, headers) exists but is beyond the scope of the book.

Example

CDN servers in San Francisco → users in Los Angeles get content faster than users in Europe.

Client → Origin
120ms
Client → CDN
40ms

The CDN edge answers ~3× faster than the distant origin server.

The CDN is essentially a geographically distributed cache for static files. The race shows the book's example numbers: 120 milliseconds to the origin versus 40 to a nearby CDN edge.
CDN workflow · Figure 1-10

Step by step: image.png

1
User A requests image.png via a URL whose domain is provided by the CDN provider:
mysite.cloudfront.net/logo.jpg
mysite.akamai.com/image-manager/img/logo.jpg
2
Not in the CDN cache → the CDN requests the file from the origin (a web server or storage like Amazon S3).
3
Origin returns image.png with an optional HTTP header Time-to-Live (TTL) — how long it stays cached.
4
CDN caches the image and returns it to User A. It stays cached until the TTL expires.
5
User B requests the same image.
6
The image is returned from the cache as long as the TTL hasn't expired.
Step through with the arrow key — each press reveals one step on the diagram and in the list. The key point: only the first request goes to the origin; every following request within the TTL is served by the edge.
Considerations of using a CDN

Four things to get right

Cost

CDNs are run by third-party providers and you're charged for data transfers in and out. Caching infrequently used assets gives no real benefit — move them out of the CDN.

Appropriate cache expiry

For time-sensitive content, expiry should be neither too long (content no longer fresh) nor too short (repeated reloading from origin to CDN).

CDN fallback

Plan for CDN failure. During a temporary outage, clients should detect the problem and request resources from the origin.

Invalidating files

Remove a file before it expires by:

  • Invalidating the object via the CDN vendor's API
  • Object versioning: image.png?v=2
Reveal one card at a time. Cost — you pay for transfer, so don't put cold assets there. Expiry — same trade-off as cache TTL. Fallback — the CDN itself can fail. Invalidation — either call the vendor API or change the URL with a version parameter so clients fetch the new file.

Section 03

Stateless Web Tier

To scale the web tier horizontally, move state (e.g. user session data) out of the web servers.

Section three: stateless web tier. Store session data in persistent storage such as a relational database or NoSQL; each web server in the cluster can access it. That's a stateless web tier.
Stateful architecture · Figure 1-12

A stateful server remembers the client between requests

Stateful server: remembers client data (state) from one request to the next.
Stateless server: keeps no state information.

User A's session lives on Server 1. A request routed to Server 2 → authentication fails. So every request from the same client must hit the same server.

Sticky sessions help… but

  • Add overhead to the load balancer
  • Adding / removing servers is much harder
  • Server failures are hard to handle
In a stateful setup, User A's session and profile image are stored on Server 1 only. If the load balancer sends A to Server 2, authentication fails. Load balancers can use sticky sessions, but then you can't freely add or remove servers or survive a server crash.
Stateless architecture · Figure 1-13

Any request → any server

HTTP requests from users can be sent to any web server, which fetches state data from a shared data store.

State is stored in the shared store and kept out of web servers.

Simpler
More robust
Scalable
Now the servers are interchangeable. Whichever server gets the request fetches the session from shared storage. This is what makes horizontal scaling and autoscaling trivial.
Updated design · Figure 1-14

Stateless web tier + auto scaling

Session data → NoSQL

The shared store could be a relational DB, Memcached/Redis, or NoSQL. NoSQL is chosen because it is easy to scale.

1Auto scale

Autoscaling = adding or removing web servers automatically based on traffic load — easy once state is out of the web tier.

The site grows and attracts users internationally → supporting multiple data centers becomes crucial.
Session data moved to NoSQL. The web tier can now grow from two to four servers — or shrink — automatically. Next, as users come from all over the world, one data center is no longer enough.

Improve availability and user experience across wider geographical areas.

Section four: multiple data centers.
Data centers · Figures 1-15 & 1-16

GeoDNS routing — and failover

geoDNS resolves domain names to IP addresses based on the user's location, so users are routed to the closest data center.

Multi-data center setup

Technical challenges to solve

Traffic redirection

Effective tools are needed to direct traffic to the correct data center. GeoDNS routes users to the nearest one.

Data synchronization

Users in different regions may use different local databases or caches. In failover, traffic may land where data is unavailable. Common strategy: replicate data across data centers (e.g. Netflix's asynchronous multi-DC replication).

Test & deployment

Test your website/application at different locations. Automated deployment tools keep services consistent across all data centers.

To scale further we need to decouple components so they scale independently — the message queue is the key strategy used by many real-world distributed systems.
Three challenges: getting traffic to the right place, keeping data in sync so failover actually works, and deploying consistently everywhere. Then transition: to keep scaling, we decouple components — message queues.

Message Queue

A durable component, stored in memory, that supports asynchronous communication.

Section five: message queue.
Message queue · Figure 1-17

Producers publish, consumers subscribe

It serves as a buffer and distributes asynchronous requests.

Producer

a.k.a. publisher — creates messages
publish →
→ consume

Consumer

a.k.a. subscriber — performs the action

Consumer is down?

The producer can still post messages to the queue.

Producer is down?

The consumer can still read messages from the queue.

Decoupling makes the message queue a preferred architecture for building scalable and reliable applications.
Producers create messages and publish them to the queue; consumers connect and perform actions defined by the messages. Because they don't talk directly, either side can be unavailable without breaking the other.

Cropping, sharpening, blurring… take time. Web servers publish jobs; workers pick them up and process them asynchronously.

Two broad approaches: vertical scaling and horizontal scaling.

Section seven: database scaling.
Vertical vs. horizontal · Figure 1-20

Scale up — or scale out?

Vertical scaling · scaling up

Add more power (CPU, RAM, DISK) to an existing machine.

10M+

Serious drawbacks

  • Hardware limits — a single server isn't enough for a large user base
  • Greater risk of single point of failure
  • High cost — powerful servers are much more expensive
VS
Vertical

Bigger machine

Horizontal · sharding

More servers

Vertical scaling works surprisingly far — Stack Overflow ran on one master in 2013 — but it hits hardware limits, is a SPOF, and gets expensive. Horizontal scaling, also known as sharding, adds more servers instead.
Horizontal scaling · Figures 1-21 & 1-22

Sharding: split a large database into shards

Each shard shares the same schema, but the data on each shard is unique. A hash function picks the shard for every read/write.

user_id % 4
Sharding key (partition key): one or more columns that determine how data is distributed — here user_id. It routes queries to the correct database. Choose a key that distributes data evenly.
The demo routes random user IDs automatically; you can also type one and press Route. user_id modulo 4 picks one of four shards. Emphasize: the most important decision is the sharding key, and it must spread data evenly.
Sharding is far from perfect

New complexities and challenges

Resharding data

Needed when 1) a single shard can't hold more data due to rapid growth, or 2) uneven distribution causes shard exhaustion. Requires updating the sharding function and moving data. Consistent hashing (Chapter 5) is the common fix.

Celebrity problem

a.k.a. hotspot key. Katy Perry, Justin Bieber and Lady Gaga all on one shard → that shard is overwhelmed with reads. Fix: a shard per celebrity, maybe further partitioned.

S0
S1 🔥
S2
S3

Join & de-normalization

Once sharded across servers, joins across shards are hard. Common workaround: de-normalize the database so queries can be performed in a single table.

Three challenges. Resharding when a shard fills or data is uneven — consistent hashing solves this later in chapter five. The celebrity or hotspot problem — one shard gets hammered. And joins — you can't easily join across servers, so we de-normalize.
