1.1 · Introduction to databases

A database is a set of related information

A telephone book is a database: names, numbers and addresses for one region. It also shows exactly what a paper database can't do — and why some of the first computer programs ever written were database systems: computerized storage and retrieval.

Slow to search

Finding one number in a big book takes real time.

→ A database system retrieves data in milliseconds.

Indexed one way only

It's sorted by last/first name. "Who lives at 12 Elm St?" is possible in theory, useless in practice.

→ A database can index the same data in many ways.

Stale on day one

People move and change numbers the moment it's printed.

→ A database serves up-to-the-minute data.

Then → nowEarly systems stored data on magnetic tapes, with technicians loading tapes on request and re-reading them for every repeated query. Modern systems manage petabytes, accessed by clusters of servers that each cache tens of gigabytes in high-speed memory.

1.2 · Nonrelational systems · hierarchical

Hierarchical model: data as trees

Figure 1-1 from the book. Pick a question to see how the system answers it.

George and Sue each get their own tree: customer → accounts → transactions. The system finds one customer's tree, then traverses it.

Single-parent hierarchy

Every node has zero or one parent and zero, one or many children.

Questions that follow the tree's shape are fast. Questions that cut across trees ("all big debits") mean walking every tree.

You know thisThe DOM is a single-parent hierarchy: every node has one parent and any number of children.

1.2 · Nonrelational systems · network

Network model: records plus explicit links

To find the transactions on Sue's money market account:

  1. 1Find the customer record for Sue Smith.
  2. 2Follow the link from her record to her list of accounts.
  3. 3Traverse the chain of accounts until you reach money market.
  4. 4Follow the link from that account to its list of transactions.

Multi-parent hierarchy

Each product record (Checking, Savings…) also links to every account of that type. An account is reachable from its customer and its product.

The catchIn both models, relationships are explicit links, so every question is a navigation path you have to walk by hand.

2.1 · The relational model

1970: everything becomes a table

E. F. Codd of IBM published A Relational Model of Data for Large Shared Data Banks: represent data as sets of tables, and instead of pointers, link rows with redundant data — matching values stored in both places. Same bank, relational version (Figure 1-3). Click any row.

Nothing selected. Every lit row you'll see is reachable purely by matching values — no pointers anywhere.

2.2 · Primary keys

A primary key is a row's identity

◆ Primary key

One or more columns whose value uniquely identifies each row. cust_id = 1 is George, forever; nothing else is needed to find him.

Compound key

A primary key made of two or more columns, e.g. (fname, lname).

Natural vs surrogate

Natural: built from real-world data (a name). Surrogate: a value invented just to be the key (cust_id). Every server can generate unique numbers for you.

RulePrimary key values must never change once assigned. Names change — so names make bad keys.

2.3 · Foreign keys and joins

Foreign keys: relationships stored as values

A foreign key is one or more columns that identify a single row in another table. They do the job the arrows did in the older models. Taking a foreign key value and finding the matching row is called a join.

Find George Blake's checking transactions:

  1. 1In customer, find George Blake → cust_id = 1.
  2. 2In product, find "Checking" → product_cd = 'CHK'.
  3. 3In account, find the row with cust_id = 1 and product_cd = 'CHK' → account_id = 103.
  4. 4In transaction, take every row with account_id = 103.

Four lookups, zero pointers. This matching of a foreign key to its row is called a join; SQL can do all four lookups in a single statement, which you'll see at the end of this chapter. Joins get their own chapters later.

2.5 · Redundancy and normalization

One fact, one place

Allowed

account.cust_id — storing another row's key. That's the only redundancy the model wants.

Not allowed

Copying the customer's name into account. Change it in one place and the other copy lies.

Not allowed

One column holding several facts: name = first + last, address = street, city, state, zip.

Refining a design until each independent piece of information lives in exactly one place (foreign keys excepted) is normalization. Watch what happens without it:

Both sides run UPDATE … WHERE account_id = 105 or its normalized equivalent.

3.2 · SQL statement classes

Three kinds of statements

Schema

Define the structures data lives in.

CREATE TABLE corporation
 (corp_id SMALLINT,
  name VARCHAR(30),
  CONSTRAINT pk_corporation
    PRIMARY KEY (corp_id)
 );

Data

Manipulate what's inside: select, insert, update, delete.

INSERT INTO corporation
  (corp_id, name)
VALUES (27, 'Acme Paper Corporation');

SELECT name
FROM corporation
WHERE corp_id = 27;

Transaction

Begin, end and roll back transactions. You'll meet them properly in Chapter 12.

Data dictionaryEverything created by schema statements is recorded in special tables: metadata, "data about the database". You can query them with SELECT just like your own tables (Chapter 15). Most of this book is about the data statements: select, update, insert and delete.

3.3 · SQL is nonprocedural

You describe the result. The optimizer picks the path.

A procedural language defines the result and the process that produces it. A nonprocedural one defines only the result; an external agent decides how to get there.

// procedural: you own the loop
const out = [];
for (const c of customers)
  if (c.lname === 'Smith')
    out.push({ cust_id: c.cust_id, fname: c.fname });
-- nonprocedural: you own the "what"
SELECT cust_id, fname
FROM customer
WHERE lname = 'Smith';

The optimizer

That agent is a part of the database engine. It looks at your SQL, at how your tables are configured and at which indexes are available, then decides the most efficient execution path (well, not always the most efficient).

Optimizer hints

Most engines let you influence it, for example by suggesting an index. Most SQL users never get that far and leave it to a database administrator or performance expert.

You know thisImperative DOM code vs React: you declare the UI, the reconciler decides which DOM operations to run. The optimizer is SQL's reconciler.

4.1 · Anatomy of a query

SELECT, FROM, WHERE — and the order to write them

SELECT /* one or more things */ ...
FROM   /* one or more places */ ...
WHERE  /* one or more conditions apply */ ...

Almost every query has these three clauses. The book's advice for writing one:

  1. 1FROM — which table(s) hold the data?
  2. 2WHERE — which rows don't you want?
  3. 3SELECT — which columns go in the result?

Text between /* and */ is a comment, as is anything after -- on a line.

SELECT txn_id, amount
FROM transaction
WHERE account_id = 105;

4.2 · Changing data

INSERT and UPDATE — and read "rows affected"

An UPDATE has a WHERE clause too: it picks the rows to change. The book's product_cd is the primary key, so you should expect exactly one row modified (or zero if the value doesn't exist). Whenever you run a data statement, the engine reports how many rows were returned, created, modified or removed. Try the presets in order, then experiment freely.

ClassicCheck the row count: it tells you if a statement did something unexpected, like a DELETE with no WHERE clause, which removes every row in the table. Programs get the same count from their toolkit after each statement.

5 · What is MySQL? · SQL unplugged

Where SQL runs

Commercial

Oracle Database, Microsoft SQL Server, IBM DB2. Some are better at very large or high-throughput workloads, some at objects, large files or XML.

Open source

PostgreSQL and MySQL. The book runs everything on MySQL 8.0 — but it's a book about SQL, not MySQL: its statements run on Oracle, DB2 and SQL Server with few or no changes.

SQL unplugged

Hadoop, Spark, NoSQL and NewSQL: distributed systems on clusters of commodity servers — and they still speak SQL. Tools like Apache Drill can query across databases, JSON, CSV and log files at once (Chapter 18).
